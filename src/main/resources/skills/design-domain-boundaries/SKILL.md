# 领域边界与聚合根

使用DDD发现稳定的业务语义、职责和一致性边界。聚合根提取是本技能的核心产物。

独立执行协议：稳定ID使用 `{PROJECT}-{TYPE}-{DOMAIN}-{SEQUENCE}`，序号不复用；证据状态只用 `SOURCE_FACT/CONFIRMED/INFERRED/PROPOSED/OPEN/REJECTED/RETIRED`。结束时返回 `status, gate, gate_status, continuation_required, next_work_item_id, next_stage, stop_reason, discovered_items, registered_ids, confirmed_ids, unconfirmed_ids, artifacts, added_ids, changed_ids, retired_ids, blockers, upstream_revision, next_allowed_stages, evidence`；被总入口调用时保留调用方的项目、切片和基线版本。

## 铁律：逐项发现、登记、确认并继续

每个术语、子域、上下文、关系、聚合候选、不变式、命令和领域事件必须先从场景/规则发现，以稳定ID追加到全局 `00-control/work-item-registry.csv`，并把明细追加到 `ubiquitous-language.csv`、上下文主清单、`aggregate-catalog.csv`、`domain-events.csv` 等对应CSV；再经压力测试与边界一致性复核后回写同一CSV行确认。只在回复/Markdown说“已登记”、只返回 `registered_ids` 或CSV只有表头均不算登记。未登记的对象不得塞入领域图，未确认聚合不得驱动物理表或代码包。确认一项后继续下一候选；清单闭合后自动执行G3并路由数据/后端，不因生成聚合目录而停止。

## 准入

消费G2通过的 `SCN/BR/STM/TRN/PERM/CMD/DATA/INT`。存在代码库时同时消费GF通过范围内的 `MOD/COMP/XAPI/XTBL/EXT/REUSE/GAP`；它们是实现约束和复用证据，不是业务规则或领域边界的来源。输入不完整时可输出候选，但不得把候选不变式标为已确认。

若输入只有字段表，不输出聚合候选；先回到需求/场景阶段补齐行为、规则、不变式和生命周期证据。

若输入只有自然语言且项目代码已知，按统一产物协议创建状态为 `PROPOSED` 的稳定ID；项目代码也未知时只使用明确标注为临时、不可登记的 `CAND-*` 引用，并把补建正式ID列为阻塞项。

## 工作流

1. 建立通用语言：术语、定义、上下文、同义词、禁用词、来源和歧义。
2. 按业务目标、价值、流程、规则所有者、数据权威和变化原因形成子域候选；不按菜单或组织架构切分。
3. 串联场景：`角色/触发 -> 命令 -> 规则 -> 状态/事件 -> 后续/异常`。
4. 识别限界上下文：使命、包含/排除、术语、数据权威、公开能力、上下游、变化原因。
5. 建立上下文关系：上游/下游、契约、翻译/防腐、同步时延、失败责任和数据所有者。
6. 对每个命令询问：一次操作结束时哪些对象的哪些条件必须共同成立？列出具体不变式。
7. 结合共同生命周期、受控修改入口、并发、强一致、补偿、人工恢复和快照识别一致性单元。
8. 提取聚合根，列内部实体/值对象与明确排除项；用主/异常/并发/恢复场景压力测试。
9. 识别领域事件作为业务事实；同步事务、进程内事件、可靠消息是后续实现决策。
10. 建立设计到已确认实现架构和现有能力的候选映射；优先引用批准的 `REUSE/EXTEND/ADAPT` 决策。现有模块、Service或旧表与上下文/聚合不一致时明确转换边界，不反向改变业务设计。架构尚未决定时才比较三层、四层、模块化单体和微服务，不在此强制选型。
11. 执行Gate G3并返回结构化阶段结果。

## 聚合根提取协议

每个 `AGG-*` 必须输出：

- 上游 `SCN/CMD/BR/STM/PERM/DATA`；
- 根名称、ID和受控修改入口；
- 内部实体/值对象及排除项；
- 逐条不变式及违反表现；
- 命令、状态迁移、事件、副作用；
- 事务边界、并发策略和失败恢复；
- 与其他聚合的ID、快照或契约关系；
- 仓储/持久化入口候选；
- 置信度、替代方案和开放问题。

提取顺序：场景链→命令/结果→不变式→生命周期/并发→一致性单元→根候选→压力测试。

## 架构中立

- 三层：聚合修改入口可映射到业务Service，规则映射到Service内部规则类/策略/实体方法，DAO负责持久化。
- 四层/Clean/Hexagonal：按依赖方向映射；Port不等于聚合根接口，Clean Entity不必然等于DDD聚合根。
- 模块化单体：上下文优先映射模块公开契约，内部类和表不外泄。
- 微服务：只有独立部署、团队、性能、安全或发布收益成立时才选择。

用户已明确保留三层等架构时，只输出该架构的最小映射和风险；不展开无关架构。需要包、目录或API细化时再交给后端技能。

已有BPM、文件、组织权限、字典、通知等基础能力只映射为协作者或基础设施契约；不得把它们并入业务聚合，也不得因其存在而复制通用能力。

## 禁止机械规则

不允许用以下等式替代设计：上下文=微服务、聚合=微服务、聚合=表、跨聚合=消息、实体=充血模型、一次事务绝不跨聚合。它们只能作为候选启发式并记录权衡。

## Gate G3

- 术语、规则、状态和数据有权威归属；
- 上下文含包含/排除和公开契约；
- 每个聚合候选有具体不变式；无不变式时不造聚合；
- 一致性、事务、并发和恢复由业务要求支撑；
- 设计边界与部署/代码分层分开；
- 循环、多写入者和跨边界直写已处理或阻塞。
