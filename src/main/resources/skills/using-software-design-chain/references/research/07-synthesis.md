## 一、七个核心心智模型

### M1 证据先于完整

- 一句话：宁可显式留下问题，也不把经验性猜测写成已确认需求。
- 生成力：面对缺字段、冲突文档、未定义状态、模糊权限时，先建立 `ISSUE/CONFLICT/DEC/ASM`，再决定是否继续。
- 应用：需求精炼、边界判断、表设计、接口错误语义、验收口径。
- 局限：探索性原型可以带假设前进，但不得提升为正式基线。

### M2 行为先于结构

- 一句话：先明确谁在何时基于什么规则改变什么业务事实，再设计表、类、接口和页面。
- 生成力：字段表只能产生数据候选；只有场景、命令、规则、状态、权限和异常闭环后，才能稳定推导结构。
- 应用：阻止“一张表单一张表”“一个页面一个 CRUD”“菜单就是业务边界”。
- 局限：已有系统重构必须同时把旧表和旧接口作为现实约束。

### M3 边界稳定，实现可替换

- 一句话：DDD用于识别语义、职责和一致性边界，三层、四层、模块化单体或微服务是独立的实现决策。
- 生成力：同一领域模型可以映射到三层 `service`、四层 `domain/application`、模块或服务，但必须能定位规则、事务、数据所有者和公开契约。
- 应用：限界上下文、聚合根、事务边界、代码分包、部署决策。
- 局限：边界也会随业务变化，不能冻结为永恒组织图。

### M4 聚合由不变式产生

- 一句话：聚合根不是主表、父对象或页面标题，而是保护一组业务不变式的受控修改入口。
- 生成力：对每个命令询问“一次操作结束时哪些条件必须共同成立”，再结合生命周期、并发、事务、失败恢复和快照需求识别聚合。
- 应用：输出聚合根、内部实体/值对象、命令、事件、事务范围和仓储候选。
- 局限：查询、报表、批处理和简单 CRUD 不必强造聚合。

### M5 一个基线，多种投影

- 一句话：数据、后端、前端和测试是同一业务基线的不同投影，不得各自发明规则。
- 生成力：同一 `SCN/BR/STM/PERM` 应分别映射到 `TBL/API/PAGE/TC`，任何孤儿项都是设计缺口。
- 应用：有限并行、纵向切片、变更影响分析、最终一致性审查。
- 局限：不同投影可以为了性能或体验冗余，但必须声明权威来源和同步方式。

### M6 契约先于目录

- 一句话：先定义用例、权限、事务、输入输出、错误、审计和副作用，再决定 Controller、Service、Domain、DAO 或 Adapter 放在哪里。
- 生成力：架构风格不再由模板决定，而由现有项目、复杂度、团队、发布、性能、安全和运维能力共同决定。
- 应用：OpenAPI、Service接口、事件契约、错误目录、代码边界和集成对账。
- 局限：纯内部原型可简化契约形式，但不能省略业务语义。

### M7 质量门控制增量演进

- 一句话：八阶段是可回退的有向图，不是严格瀑布，也不是无限自由循环。
- 生成力：每阶段有准入、产物、退出 Gate、结构化状态、回退目标和无进展停止条件。
- 应用：总入口路由、并行控制、版本管理、问题闭环和完成证据。
- 局限：Gate 不能变成追求文档完美的官僚流程；应按风险和纵向切片缩放。

## 二、十条决策启发式

1. 如果能力缺少参与者、触发、业务结果或异常，则保留为能力种子，不升级为可开发场景。
2. 如果状态迁移缺少执行者、守卫、权限、副作用或失败处理，则阻塞下游设计。
3. 如果一组对象必须在一次命令结束时共同满足具体不变式，则把它们列为聚合候选，并继续验证生命周期、并发和事务代价。
4. 如果找不到可陈述的不变式，则不要为了DDD形式强造聚合根。
5. 如果业务记录未来仍需证明“当时是什么”，则明确快照；否则默认引用权威主数据并显示来源时间。
6. 如果出现“实时”，则改写为可测试的新鲜度、同步频率、延迟、时间戳和失败补数契约。
7. 如果聚合、表、模块、API、页面或微服务被画成一一对应，则要求逐项给出业务或非功能依据。
8. 如果页面动作不能追踪到用例/API/规则/状态，或API不能追踪到业务场景，则判定断链。
9. 如果下游发现上游语义错误，则提交带受影响ID的 `REVISE_UPSTREAM`，不得静默改写。
10. 如果同一问题回退一次后仍无新证据，或连续两轮没有实质变化，则停止并转 `NEEDS_CONTEXT/BLOCKED`。

## 三、聚合根提取协议

`design-domain-boundaries` 必须支持聚合根提取，并为每个 `AGG-*` 输出：

- 上游 `SCN/CMD/BR/STM/PERM/DATA` 引用；
- 聚合根名称、身份和受控修改入口；
- 包含的实体和值对象，以及明确排除项；
- 逐条可验证的不变式；
- 命令、状态迁移、领域事件和失败恢复；
- 强一致范围、事务边界、并发策略；
- 与其他聚合的ID/快照/契约关系；
- 仓储或其他持久化入口候选；
- 置信度、替代方案、开放问题和提取依据。

提取顺序：场景链 → 命令与结果 → 不变式 → 生命周期/并发 → 一致性单元 → 根候选 → 边界压力测试。不得从主外键、页面父子结构或固定对象数量直接确定聚合。

## 四、数据库表生成阶段

数据库表在第4阶段 `design-data-model` 正式生成，不在聚合阶段生成。

### 第2阶段提供数据种子

- 字段定义、基数、条件必填、权威来源、敏感级别、历史意图；
- 业务状态、权限和审计需求；
- 不得输出最终表名和DDL结论。

### 第3阶段提供数据所有权和一致性依据

- 限界上下文、聚合根、实体/值对象、快照候选、不变式、事务范围；
- 不直接把聚合映射为单表或表簇。

### 第4阶段依次生成

1. 概念模型：业务实体、关系、基数、所有者、生命周期；
2. 逻辑模型：属性、候选键、关系拆分、规范化、主数据/快照/历史/派生数据；
3. 物理模型：表、列、数据库类型、PK/FK/UQ/CK、索引、分区候选、租户列、审计列、归档与删除；
4. 数据字典：字段语义、来源、可空性、精度、时区、枚举、敏感和历史策略；
5. 映射矩阵：`DATA/AGG/BR -> TABLE/COLUMN/CONSTRAINT`；
6. DDL：只有数据库类型/版本、命名规范、数据量、查询模式和迁移边界已确认后才生成可执行DDL；否则输出引擎中立物理模型与阻塞项。

物理表可以与聚合一对多、多对一或通过读模型冗余，前提是权威写入者、不变式、同步和审计关系明确。

## 五、统一质量门

| Gate | 阶段 | 核心通过条件 |
|---|---|---|
| G0 | 入口 | 来源、项目、切片、版本、范围可识别 |
| G1 | 需求 | 范围、角色、目标、术语、Must/NFR和重大冲突可判定 |
| G2 | 场景 | 主/异常流程、规则、状态、权限、审计闭环 |
| G3 | 边界 | 上下文、数据权威、聚合不变式、事务和失败恢复明确 |
| G4 | 数据/后端 | 三层数据模型完整；写用例具备权限、事务、并发、幂等、错误、审计 |
| G5 | 前端 | 页面动作、字段、状态、权限和API收敛 |
| G6 | 测试 | Must/NFR、规则、状态、权限、契约均有可执行验证 |
| G7 | 全链 | 无阻塞/严重断链；豁免有责任人、理由、期限和决策ID |

## 六、统一产物协议

稳定ID格式：`{PROJECT}-{TYPE}-{DOMAIN}-{SEQUENCE}`。序号永不复用，不包含年份、版本、状态、章节号或文件路径。

主要类型：`SRC/GOAL/SCOPE/TERM/ACT/CAP/REQ/SCN/BR/STM/TRN/PERM/FLD/DATA/CTX/AGG/CMD/EVT/TBL/UC/API/SVC/PAGE/ACTION/TC/AC/NFR/INT/DEC/ISSUE/ASM`。

典型链路：

`SRC/CAP/REQ -> SCN -> BR/STM/PERM -> CTX/AGG/CMD -> DATA/TBL -> UC/API/SVC/EVT -> PAGE/ACTION -> TC/AC`

每项最少记录：`id/type/title/status/version/owner/source_refs/confidence/upstream_refs/decision_refs/verification_refs`。

统一阶段状态：`READY`、`READY_WITH_ASSUMPTIONS`、`NEEDS_CONTEXT`、`BLOCKED`、`REVISE_UPSTREAM`、`FAILED_VALIDATION`。

## 七、表达与操作DNA

- 结论先行，随后给依据、替代方案和影响；
- 严格区分 `SOURCE_FACT/CONFIRMED/INFERRED/PROPOSED/OPEN/REJECTED`；
- 用表格表达精确映射，用流程图表达依赖，不用大段口号代替设计；
- 业务术语优先于框架术语；首次出现的技术词给出简明解释；
- 不以DDD、微服务、低代码或任何框架名称代替决策依据；
- 不输出 `TBD/TODO/按实际情况` 等伪完成内容，未知内容进入问题台账；
- 每次交付说明新增、修改、废弃、冲突、断链和下一允许动作。

## 八、价值排序、反模式与张力

价值排序：可追踪真实性 > 业务语义 > 可实现性 > 可验收性 > 架构纯度 > 文档数量。

主要反模式：从字段直接建表、从菜单划边界、一个聚合一个微服务、页面直改状态、按钮隐藏代替授权、HTTP 200代替业务成功、只有主流程测试、下游静默改写上游、把文件存在当作阶段完成。

核心张力：完整性与交付速度、强Gate与迭代探索、业务纯度与遗留约束、强一致与解耦、复用与边界自治。技能应记录权衡，而不是假装张力不存在。

## 九、诚实边界

- 文档无法自动提供未写明的业务规则、权限裁决和组织责任；
- 聚合根提取是证据驱动的设计判断，不是唯一数学答案；
- 最终DDL依赖数据库引擎/版本、数据规模、查询模式、保留和迁移要求；
- 代码目录映射依赖真实仓库、技术栈和现有约定；
- 高保真前端仍需要设计系统、终端约束和真实用户验证；
- 测试与验收可先设计，但执行需要环境、数据、外部依赖和责任人；
- 本框架控制设计质量，不替代业务负责人、数据负责人、架构师和验收责任人的批准。
