## 0. 研究范围与标记

- 目标：研究企业管理软件从“角色/场景/规则/状态/权限”推导前端设计，再推导测试与验收的方法。
- 本文件只提供研究证据和方法候选，不定义最终 Skill 的执行指令。
- **事实**：可由用户材料、标准或权威文档直接支持。
- **推断**：基于事实形成的工程建议，需在 Skill 构建阶段评审。
- **待确认**：用户材料中缺失、冲突或不能安全假设的事项。
- 本地材料：`项目建设方案-国资运营科创管理系统v0.7(1).docx`、`科研系统要素梳理(1).docx`、用户上传《中台架构与实现：基于DDD和微服务》EPUB。

## 1. 权威依据中的事实

### 1.1 从用户任务到页面

- **事实**：用户上传《中台架构与实现》第18.2.2节把场景分析定义为从用户视角识别场景、用例操作和子域依赖；示例会从前端操作一直梳理到命令、领域事件和外部依赖。
- **事实**：该书第20—21章提出前端页面逻辑仍应服务完整业务场景；微前端是否采用、如何拆分必须结合具体业务场景，而不是机械复制后端服务边界。
- **事实**：该书说明用户接口层可通过 DTO/facade 适配前端；跨服务组合也可由应用服务或 BFF 承担，使前端不承担后端服务编排。
- **事实**：该书将“业务边界”作为微服务与微前端组合的分析基准，但同时强调具体情况具体分析。
- **事实**：GOV.UK Service Manual 要求从端到端服务考虑用户接触的工具、交易、支持和线下步骤，并用真实用户测试设计与原型。[GOV.UK：User research in alpha](https://www.gov.uk/service-manual/user-research/user-research-in-alpha)
- **事实**：受控可用性测试通过观察参与者完成具体任务，验证用户是否理解、能否完成，并发现语言或布局问题。[GOV.UK：Moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)
- **推断**：前端设计的基本单位应是“角色要完成的任务/业务场景”，不是数据库表，也不必等同于聚合或微服务。
- **推断**：领域边界适合约束页面职责、术语和数据归属；页面可为完成一个用户任务组合多个边界的只读信息或命令接口。

### 1.2 权限是角色、对象、动作和上下文的组合

- **事实**：NIST RBAC 将权限赋予角色，再把用户分配给角色；角色可表达组织中的工作职能。[NIST：RBAC Models](https://csrc.nist.gov/csrc/media/projects/role-based-access-control/documents/sandhu96.pdf)
- **事实**：NIST ABAC 把主体、对象、请求操作和环境属性纳入授权决策；这补充了纯 RBAC 对对象级、组织范围和上下文约束的不足。[NIST SP 800-162](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-162.pdf)
- **事实**：OWASP ASVS 5.0 要求记录授权规则及其决策因素/环境上下文，并确保调用者只能访问其授权资源。[OWASP ASVS V8](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x17-V8-Authorization.md)
- **事实**：OWASP API Security 要求所有接收对象 ID 并操作对象的端点执行对象级授权检查。[OWASP API1:2023](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)
- **推断**：前端“隐藏按钮”只是体验表现，服务端仍必须逐请求校验；测试必须分别覆盖页面可见性和 API 越权防护。
- **推断**：企业系统的可用操作不能只写“某角色可编辑”，应表达为：`主体角色/岗位 + 数据组织范围 + 对象归属 + 业务状态 + 工作流状态 + 渠道 + 动作`。

### 1.3 页面状态、表单反馈与跨终端

- **事实**：WCAG 2.2 是可测试的 Web 可访问性建议，适用于桌面和移动设备；W3C 建议采用最新版本作为开发目标。[W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)
- **事实**：WCAG 1.4.10 要求在等效 320 CSS 像素宽度下，除确需二维布局的内容外，信息与功能不能丢失，也不应要求二维滚动。[W3C：Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- **事实**：WCAG 3.3.1 要求自动发现输入错误时，标识出错项并以文本描述错误；仅重新显示表单不够。[W3C：Error Identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html)
- **事实**：WCAG 4.1.3 要求成功、等待、进度和错误等不夺取焦点的状态消息可被辅助技术识别。[W3C：Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)
- **事实**：GOV.UK Design System 建议在字段旁和错误摘要中说明“哪里错了、如何修复”，并保留用户已输入内容。[GOV.UK：Error message](https://design-system.service.gov.uk/components/error-message/)
- **事实**：GOV.UK 的“Check answers”模式让用户在最终提交前复核信息。[GOV.UK：Check answers](https://design-system.service.gov.uk/patterns/check-answers/)
- **推断**：每个异步或可编辑页面都应有明确的 `loading / success / empty / validation-error / forbidden / conflict / unavailable` 等状态，而不是只画正常态。
- **推断**：PC 与移动端应做“渠道能力矩阵”，不能仅把 PC 页面压窄；外勤移动场景应优先快速录入、拍照/附件、待办与弱网恢复。

### 1.4 验收与追踪

- **事实**：ISTQB Acceptance Testing 覆盖 UAT、合同/监管验收、业务流程/规则建模，以及可用性、性能和安全等非功能验收。[ISTQB CT-AcT](https://istqb.org/certifications/certified-tester-acceptance-testing/)
- **事实**：Cucumber Gherkin 用 `Given` 描述初始上下文、`When` 描述事件、`Then` 描述可观察结果；`Rule` 可把场景归属于业务规则。[Cucumber Gherkin](https://cucumber.io/docs/gherkin/reference/)
- **事实**：ISTQB Foundation v4.0.1 把状态迁移测试用于覆盖状态和转换；一个用例可以覆盖多个连续转换。[ISTQB CTFL 4.0.1](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)
- **事实**：NASA 软件工程手册指出双向追踪保证每项需求在设计、实现和测试中被覆盖，也能识别没有需求依据的额外实现。[NASA：Requirements traceability](https://swehb.nasa.gov/plugins/viewsource/viewpagesrc.action?pageId=215777306)
- **事实**：NASA 指出追踪矩阵可连接需求、设计、代码、测试计划、步骤、用例和测试数据，并用于变更影响分析。[NASA SWE-072 guidance](https://swehb.nasa.gov/plugins/viewsource/viewpagesrc.action?pageId=32604549)
- **推断**：验收不应只维护“需求→测试用例”，而应维护 `需求→规则/状态/权限→页面/API/表→测试→结果/缺陷` 的双向链。

### 1.5 API、集成、迁移和性能

- **事实**：OpenAPI 为 HTTP API 提供与编程语言无关、可由人和机器理解的接口描述。[OpenAPI 3.2](https://spec.openapis.org/oas/v3.2.0.html)
- **事实**：Pact 的消费者驱动契约以消费者实际使用的请求和最小响应期望形成契约，再由提供者验证。[Pact：How Pact works](https://docs.pact.io/getting_started/how_pact_works)
- **事实**：OpenID Connect Core 定义客户端如何基于授权服务器完成的认证来验证最终用户身份。[OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)
- **事实**：OWASP 指出 SSO 常存在应用会话和 SSO 会话并存，退出测试需分别验证应用退出、SSO退出及再次访问受保护页面。[OWASP：Testing logout](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/06-Session_Management_Testing/06-Testing_for_Logout_Functionality)
- **事实**：AWS DMS 数据验证会逐行比较源端和目标端并报告不匹配；验证本身会消耗源、目标和网络资源。[AWS DMS：Data validation](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Validating.html)
- **事实**：ISTQB 性能测试资料把响应时间放在明确条件下衡量，并同时关注资源利用；代表性测试环境是结果可信的关键。[ISTQB Performance Testing syllabus](https://istqb.org/?download_id=3591&sdm_process_download=1)
- **推断**：前端联调不能用“接口可调用”代替契约；应验证字段语义、枚举、错误码、权限、并发冲突、分页、部分失败和向后兼容。
- **推断**：数据迁移验收不能只看总行数；至少需要数量、关键字段、关系完整性、转换规则、附件、权限归属和业务抽样对账。

## 2. 科创系统材料中的事实与风险

### 2.1 可直接确认的前端范围

- **事实**：系统范围包含科研项目立项、过程管控、变更、终止、验收、成果、奖项、创新载体、资讯、科创企业服务、驾驶舱和系统管理。
- **事实**：建设方案要求可配置多级审批，处理人可按角色、岗位或具体人员指定。
- **事实**：权限需结合组织层级和业务角色，限制不同单位/岗位的功能与数据范围。
- **事实**：移动端通过致远 M3 承载，包含 SSO、统一待办、企业档案查询、客户对接记录和数据双向同步。
- **事实**：客户对接记录明确要求 PC 和移动端录入，字段包括对接对象、时间、方式、成效、附件和后续待办。
- **事实**：项目详情需要呈现预算执行、里程碑、季度自查、重大事项、验收/终止状态及经费明细。
- **事实**：要素文档已有大量字段的必填/选填、来源、格式和候选值，可作为表单规则候选输入。

### 2.2 不能直接转成页面或验收标准的内容

- **事实**：项目状态仅列“初始、已立项、执行中、已验收、已终止”，没有完整覆盖审批中、退回、驳回、撤回和验收中等流程态。
- **事实**：建设方案一处要求“科研经费实时监控”，接口章节却明确财务经费每日一次回传。
- **事实**：性能章节同时出现“1000注册用户同时在线”“1000用户并发操作”“平均响应≤3秒/≤5秒”等不同口径。
- **事实**：要素文档中存在“复核指什么？”等显式未决项。
- **待确认**：科研项目的业务状态与工作流状态是否分离展示、由谁维护、哪些转换自动发生。
- **待确认**：立项、变更、终止、验收各流程的撤回、退回、驳回、转办、加签、超时和重提规则。
- **待确认**：项目负责人、单位科研管理员、集团科研管理员、审批人、财务人员、普通成员的动作和数据范围。
- **待确认**：经费看板的数据更新时间、延迟提示、失败时显示旧数据还是阻断，以及“实时”的最终业务口径。
- **待确认**：1000是在线会话数、同时活跃用户数还是同一时刻并发请求数；事务组合与峰值模型是什么。
- **待确认**：M3 是嵌入 Web、原生表单还是接口同步；弱网、重复提交、离线草稿和附件续传能力由谁提供。

## 3. 前端设计方法候选（推断）

### 3.1 前序输入完整性

- 每个前端任务必须引用 `ACTOR/SCN/RULE/STATE/PERM/DATA/API/NFR` 等稳定 ID；缺失时列为阻塞或假设。
- 先生成“角色任务清单”，再生成信息架构、页面清单和组件，不从数据库表名生成菜单。
- 每个任务记录：触发入口、目标、前置条件、主路径、异常路径、结束状态、审计证据和外部系统。
- 一个页面可服务多个相近任务，但必须能追溯到每个任务；一个任务也可跨多个页面完成。

### 3.2 信息架构与路由

- 建议产物：`角色×任务矩阵`、`信息架构树`、`页面/路由清单`、`任务→页面流`。
- 导航按用户目标和工作对象组织；后台配置、业务办理、审批待办、查询分析应避免混为同一层级。
- 列表页定义默认范围、筛选、排序、分页、批量动作、导出权限和空结果状态。
- 详情页定义摘要、业务状态、工作流状态、关键字段、关联对象、时间线、附件、审计和可用动作。
- 编辑页定义创建/编辑/只读差异、自动带出字段、跨字段规则、草稿、提交确认、并发冲突和离开保护。

### 3.3 操作与权限矩阵

- 推荐矩阵列：页面、对象、动作、角色、组织范围、对象归属、业务状态、工作流状态、渠道、前置规则、API、拒绝表现。
- 同一动作分别定义 `visible / enabled / executable`：是否显示、是否可点击、服务端最终是否允许。
- 拒绝表现区分：无权限不展示、可见但说明条件、403、对象不存在/越权统一处理、审批已被他人处理。
- 字段也需要权限：可见、脱敏、只读、可编辑、必填；不能只定义页面级权限。

### 3.4 页面状态合同

- 最低状态集：初始、加载中、部分加载、正常有数据、首次为空、筛选无结果、保存中、保存成功。
- 异常状态集：字段校验失败、业务规则拒绝、401、403、404、409并发冲突、429、外部系统超时、系统不可用。
- 集成数据需显示：来源、数据时间、同步状态、是否为旧数据、重试/人工处理入口。
- 异步动作需定义重复点击、刷新、返回、超时后结果未知、重试是否幂等。
- 所有状态都要给用户下一步；错误信息不可只有内部错误码。

### 3.5 表单合同

- 每字段记录：业务含义、控件、数据类型、必填条件、默认值、来源、格式、范围、依赖字段、可编辑状态、权限、错误文案。
- 跨字段/跨对象规则以决策表表达，例如模式、项目类型、单位不同导致的字段显隐和必填变化。
- 自动带出的项目主数据注明快照还是实时引用；历史表单不能被主数据后续修改悄然改变。
- 最终提交前显示复核摘要；提交后显示业务编号、当前状态、下一处理人或后续动作。

### 3.6 PC/M3 渠道设计

- 推荐产物：`任务×渠道能力矩阵`，每项标记完整支持、简化支持、只读、跳转 PC、不支持及原因。
- PC 适合复杂配置、长表单、批量、对比和报表；移动优先待办、查询、短表单、拍照附件和现场记录。
- 移动端仍需保持同一业务规则、状态含义和服务端权限，不能形成弱授权通道。
- 响应式验收至少覆盖窄屏重排、触控目标、软键盘、旋转、附件选择、网络切换和返回恢复。

## 4. 测试与验收方法候选（推断）

### 4.1 从规则生成可观察场景

- 每个 `RULE` 至少有正常、边界、拒绝/异常场景；每个 `STATE` 有允许和禁止的转换验证。
- 场景结构：已知角色/组织范围/对象状态/数据条件；当执行命令或外部事件到达；则观察页面、API、状态、通知、审计和下游结果。
- `Then` 优先描述用户或外部系统可观察结果；数据库断言用于技术验证，不能替代业务验收结果。
- 用决策表覆盖多条件规则，用状态迁移表覆盖合法/非法迁移，用边界值覆盖日期、金额、比例和长度。

### 4.2 分层测试组合

- 领域/Service 单元测试：计算、校验、状态转换和不变量；适配三层或四层实现，不强制存在 domain 包。
- API 测试：请求/响应 schema、错误语义、幂等、分页、并发版本、字段级与对象级授权。
- 前端组件/页面测试：条件渲染、表单规则、页面状态、键盘和辅助技术语义。
- 契约测试：PC/M3 消费者与服务提供者、科创系统与 OA/财务/天眼查接口的已用交互。
- 集成测试：真实协议、认证、重试、超时、重复消息、乱序、断点续传、补偿和对账。
- 端到端测试：只保留高价值主流程和跨系统闭环，避免用大量脆弱 E2E 代替下层测试。
- UAT：由真实业务角色在接近生产的组织、权限和数据条件下完成端到端任务。

### 4.3 必须单独建模的覆盖维度

- 权限：角色、组织上下级、本人/他人对象、项目成员关系、字段脱敏、直接调用 API、批量和导出。
- 状态：所有状态、合法转换、非法转换、重复事件、撤回/退回后重提、并发审批。
- 工作流：处理人解析、无人匹配、转办/加签、超时、流程版本变更、业务状态与流程状态一致性。
- API：schema、枚举、空值、错误码、版本兼容、消费者契约、部分成功和限流。
- 集成：OA SSO/退出、组织人员同步、待办推送、财务日同步、失败重试、重复、延迟和对账。
- 迁移：记录数、关键字段、唯一性、关系、附件、字典转换、组织/权限归属、抽样业务可用性、回滚。
- 性能：真实事务占比、并发模型、数据量、预热、思考时间、持续时长、响应分位数、成功率、资源和瓶颈。
- 可用性/无障碍：典型角色完成率、错误恢复、语言理解、键盘、缩放/窄屏、读屏状态消息。
- 审计：谁在何时以何身份对哪个对象执行什么动作、前后值、审批意见、失败动作是否记录。

### 4.4 追踪矩阵候选结构

- 行主键：`ACCEPT-xxx` 或 `TEST-xxx`。
- 来源：建设目标、需求 ID、场景 ID、规则 ID、状态迁移 ID、权限 ID、NFR ID。
- 实现：页面/路由、API operationId、服务/模块、表/字段或事件、外部接口。
- 验证：测试层级、用例、数据集、环境、自动/人工、负责人、结果、证据、缺陷。
- 变更：基线版本、最后评审时间、受影响产物、重测状态。
- 覆盖门槛候选：所有已批准高优先级需求都有验收场景；所有动作权限都有允许/拒绝测试；所有状态迁移均有覆盖。

## 5. 针对科创系统的示例性推断（非最终设计）

- `项目立项`任务流候选：创建/补充项目→配置成员和里程碑→提交→多级审批→登记立项结果→形成正式项目。
- 页面候选：计划列表/详情、项目申报编辑、提交前复核、审批工作台、项目详情、立项结果登记。
- 项目详情不宜仅显示“项目状态”；应并列业务状态、审批状态、健康度、数据更新时间及当前可执行动作。
- `项目负责人提交立项`验收应同时验证字段/跨字段规则、按钮可用性、API授权、状态转换、待办、通知和审计。
- `非本单位人员直接请求项目ID`应验证列表不可见、详情/API不可读、导出不可绕过，而不是只验菜单隐藏。
- 财务同步失败时，经费看板应验证“旧数据时间+同步异常提示”，但具体是否允许继续业务操作仍为待确认。
- M3 客户对接记录应验证重复提交、附件失败后恢复、PC可见性、组织归属、后续待办生成与双向一致性。

## 6. 质量闸门候选

- 前端设计可进入开发：每个高优先级任务都有页面流、操作权限矩阵、页面状态、表单合同和 API 引用。
- 测试可进入执行：验收口径可观察、测试数据和环境可获得、外部依赖有真实/替身策略、需求基线已确定。
- 可进入 UAT：高风险功能/权限/状态/集成测试通过，迁移演练完成，已知限制和数据时效向用户透明。
- 可验收：追踪矩阵无孤立高优先级需求，失败用例已有处置，性能口径与实测环境一致，验收证据可复核。

## 7. 反模式

- 从表结构自动生成页面并把 CRUD 当作业务任务。
- 把角色权限矩阵简化成菜单可见性，不测试对象级、字段级和 API 权限。
- 只画正常态，不设计等待、空、失败、冲突、旧数据和部分成功。
- 移动端直接缩放 PC 长表单，或因渠道不同放宽服务端业务规则与授权。
- 把接口文档、Mock 可用或 HTTP 200 等同于业务集成验收。
- 用“1000并发”一个数字替代事务模型、数据规模、持续时间、分位数和成功率。
- UAT 只做演示脚本，不让真实角色在真实权限与异常条件下完成任务。
- 追踪矩阵只在验收前补写，无法用于设计缺口和变更影响分析。

## 8. 研究结论

- **推断**：完整技能链应把前端设计和测试设计视为前序业务模型的两个投影，而不是后期美化与补测。
- **推断**：DDD 可提供边界、语言、状态和规则，但前端按用户任务组合，代码可落在既有三层 `service`，测试关注行为合同而不是包结构。
- **推断**：跨产物一致性的最小公共键应是稳定 ID；没有稳定 ID，就无法可靠实现自动审查、覆盖计算和变更影响分析。
- **待确认**：最终 Skill 是否把 WCAG 2.2 AA 设为默认质量基线，还是由项目/合同显式选择。
- **待确认**：最终 Skill 对三层项目是否默认输出 Service 内的规则归属清单，而不创建独立 domain 代码骨架。
