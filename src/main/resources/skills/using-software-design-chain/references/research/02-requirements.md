## 1. 调研边界与证据规则

本研究只使用用户提供的一手项目材料：

| 编号 | 来源 | 可证明 | 不能直接证明 |
|---|---|---|---|
| `SRC-001` | 《项目建设方案-国资运营科创管理系统v0.7(1)》 | 目标、范围、能力、集成方向、非功能目标、实施批次 | 完整流程、字段约束、权限、异常和页面验收 |
| `SRC-002` | 《科研系统要素梳理(1)》 | 候选字段、部分枚举、条件必填、字段来源线索 | 数据库表、实体关系、状态迁移、事务边界 |

后续技能必须保留四类证据标签：

- **[事实]**：原文直接陈述，必须带来源定位。
- **[分析推断]**：为使需求可执行而提出的模型或建议，必须记录验证方式。
- **[待确认]**：冲突、缺失或需要业务决策的内容，必须进入问题台账。
- **[决策]**：经授权人员确认，记录决策者、日期和替代关系。

优先级：正式决策 > 已批准基线 > 正式补充说明/会议纪要 > 建设方案 > 要素初稿 > 分析推断。同级来源冲突时不得自行选择。

## 2. 输入材料的真实定位

**[事实]** `SRC-001` 覆盖科研项目、科研资产、成果应用、奖项、创新载体、资讯、企业服务、驾驶舱、活动、分析、基础信息、移动端、迁移、系统集成、流程中心及非功能要求。

**[分析推断]** 建设方案是 `Vision + Scope + Capability/NFR Seed`，不是可直接开发的详细需求。多数条目缺少触发、前置、异常、状态、权限和可验证验收。

**[事实]** `SRC-002` 包含科研计划、项目基础、季度自查、重大事项、终止、验收、科研资产、奖项、创新企业、创新平台、资讯等要素组和若干字典候选。

**[分析推断]** 它是“表单/信息要素目录”，不是表结构。嵌套字段、重复组、多值关系、主数据引用、业务快照和状态历史尚未被建模。禁止“一张要素表直接变一张数据库表”。

## 3. 可执行需求基线的必需产物

需求技能必须输出结构化需求包，而不是扩写一篇需求说明书。

| 产物 | 必含内容 | 完成意义 |
|---|---|---|
| 来源清单 | 来源、版本、日期、所有者、权威级别、适用范围 | 所有事实可回溯 |
| 目标与范围基线 | 目标、指标、本期、后期、不做、版本、外部依赖 | 消除范围漂移 |
| 术语表 | 定义、同义词、禁用词、域、来源、状态 | 消除语言歧义 |
| 问题/冲突/决策/假设台账 | 证据双方、影响、选项、责任人、期限、结论 | 不把猜测藏进正文 |
| 能力地图 | 能力、子能力、所有者、上下游、优先级 | 建立业务全貌；不预设微服务 |
| 参与者目录 | 业务角色、系统角色、职责、数据范围、代理关系 | 为场景与权限提供主体 |
| 场景目录 | 目标、触发、前置、主流程、备选/异常、后置、审计 | 得到端到端业务闭环 |
| 规则目录 | 条件、约束/计算、例外、错误提示、生效期、来源 | 规则成为一等工件 |
| 状态机目录 | 状态、事件、守卫、执行者、副作用、失败处理 | 防止状态枚举失控 |
| 权限矩阵 | 主体、动作、资源、数据范围、字段、状态条件 | 从原则落到可开发权限 |
| 功能需求 | 原子系统义务、优先级、版本、所有者、关联场景 | 可分解和验收 |
| 数据/字段目录 | 定义、类型、基数、条件必填、来源、权威系统、编辑/历史/敏感策略 | 可交给数据设计 |
| 集成需求 | 方向、触发/频率、契约、幂等、认证、超时、重试、对账、补偿、延迟 | 可交给接口设计 |
| 非功能需求 | 工作负载、环境、指标、阈值、测量方法 | 可压测、安测、运维验收 |
| 迁移需求 | 最小集、映射、清洗、去重、失败隔离、对账、回滚 | 可实施历史迁移 |
| 验收目录 | Given/When/Then、边界、失败、拒绝、审计证据 | 可测试 |
| 追踪矩阵 | 来源/目标→能力→场景→规则/状态/权限→功能/数据/接口/NFR→验收 | 防止孤儿需求 |
| 基线清单 | 版本、工件版本、开放问题、例外、批准人 | 固化可移交状态 |

## 4. 统一编号与字段体系

使用稳定编号：`{PROJECT}-{TYPE}-{DOMAIN}-{NNN}`。编号只表达身份，不包含版本、优先级或状态；删除后不重用。

```text
KCMS-SCN-PROJ-008     科研项目验收场景
KCMS-BR-PROJ-021      验收前成果登记规则
KCMS-TRN-PROJ-012     验收通过状态迁移
KCMS-FLD-PROJ-041     申请验收时间字段
KCMS-INT-FIN-001      财务经费同步接口
KCMS-AC-PROJ-031      验收关闭条件验收标准
```

常用 `TYPE`：`SRC` 来源、`GOAL` 目标、`SCOPE` 范围、`TERM` 术语、`ACT` 参与者、`CAP` 能力、`SCN` 场景、`BR` 规则、`STM/TRN` 状态机/迁移、`PERM` 权限、`FR` 功能、`FLD/DATA` 字段/数据、`INT` 接口、`NFR` 非功能、`AC` 验收、`ISSUE/CONFLICT` 问题/冲突、`DEC` 决策、`ASM` 假设。

建议域代码：`PLAN` 科研计划、`PROJ` 项目、`ASSET` 资产成果、`AWARD` 奖项、`CARRIER` 创新载体、`INFO` 资讯、`ENT/SVC` 企业库/服务作业、`ANLY` 分析、`MASTER` 基础数据、`IAM/FLOW` 权限/流程、`OA/FIN/EXT` 外部集成、`MOBILE` 移动端、`MIG` 迁移、`AI` AI能力。

Word表中的“1、2、3”只是显示序号，不能作为字段ID。每个字段还要记录：

```yaml
id: KCMS-FLD-PROJ-041
business_name: 申请验收时间
canonical_key: project_acceptance.requested_at
form_occurrence: [项目验收申请]
source_mode: manual | generated | master_reference | external_sync | derived | snapshot
cardinality: one
required_when: "..."
edit_policy: "谁在何状态可编辑"
authority: "权威来源系统"
sensitivity: internal
history_policy: snapshot
source_refs: [SRC-002]
```

“项目中获取”必须进一步确认是实时引用还是提交时快照；“OA同步，可更改”必须拆成权威源、本地覆盖、回写、冲突和审计规则。

## 5. 需求提炼操作法

1. **原子化**：把“支持X并自动Y，异常时Z”拆成独立可验证义务。
2. **五问补全**：谁、何时、做什么、结果是什么、失败时如何处理。
3. **行为/规则/数据分离**：场景不替代规则，字段表不替代业务行为。
4. **双轨状态**：区分业务生命周期 `business_status` 与审批实例 `workflow_status`；健康度、资格有效性必要时独立。
5. **条件结构化**：把“仅浙盐股份适用，必填，单选”转成 `visible_when`、`required_when`、`value_source` 候选规则。
6. **保留不确定性**：五问无法从来源回答时建立 `ISSUE`，不编造答案。

每条功能需求最少包含 `id/title/statement/rationale/source_refs/scenario_refs/rule_refs/state_refs/permission_refs/data_refs/acceptance_refs/priority/release/owner/open_issues/assumptions`。

## 6. 需求质量门

### Gate R0：证据就绪

- 来源、版本、日期、所有者已登记，表格/修订/批注未静默丢失。
- 摘录可定位；事实、推断、待确认已分开。
- 明显复制错误和文档冲突已登记。

失败时可输出候选需求，但不得声明“基线确认”。

### Gate R1：范围与术语可判定

- 本期、后期、不做、依赖和实施批次清晰。
- 模块有所有者和版本；关键术语已统一或保留明确命名空间。
- 重大范围冲突已有决策或例外批准。

### Gate R2：场景闭环

- 每项核心能力有端到端场景和业务结果。
- 主流程、备选/异常、撤回/退回/驳回/重提等适用路径已处理。
- 外部调用包含不可用、超时、重复和数据冲突路径。

### Gate R3：规则、状态、权限闭合

- 关键状态有进入/退出条件和允许动作，自动迁移也有责任人与审计。
- 规则有范围、例外和错误提示。
- 权限覆盖功能、数据、字段、状态条件；业务状态与审批状态不混用。

### Gate R4：数据与集成可设计

- 核心字段有定义、基数、条件必填、来源、可编辑性、权威系统和历史策略。
- 接口有频率、幂等、失败、重试、对账、补偿和延迟口径。
- 数据刷新承诺不超过上游能力，或界面明确展示数据时间戳。

### Gate R5：可验收与可追踪

- 所有 Must 功能/NFR 有验收标准；NFR有环境、负载模型、指标和阈值。
- 没有无来源、无所有者、无版本、无验收的孤儿需求。
- 开放问题有风险、责任人和期限；基线已获得必要角色批准。

## 7. 常见冲突及本项目实例

| 编号 | 类型 | 文档事实 | 分析推断 | 待确认 |
|---|---|---|---|---|
| `CONFLICT-AI-001` | 范围 | AI章节写明本期不含；实施计划又安排2026年10月开发交付AI智能撰写 | 阻塞版本、预算、安全和测试范围 | 正式交付、原型还是纯后期；完成定义 |
| `CONFLICT-FIN-001` | 时效 | 经费看板要求实时；财务支出每日一次回传 | 财务实付最多日更，除非新增通道 | 数据新鲜度SLA、时间戳、失败补数 |
| `CONFLICT-PLAN-001` | 术语 | 方案/计划字段使用“直立”；项目类型含“自立项目” | 可能是错字，也可能是模式与类型两个概念 | 两者定义、规范名、映射和历史取值 |
| `ISSUE-PROJ-001` | 状态 | 项目仅初始/已立项/执行中/已验收/已终止；又存在多级审批、变更、验收和终止流程 | “初始”无法表达草稿、审批中、退回等；需双轨状态 | 完整业务状态和工作流状态 |
| `CONFLICT-INFO-001` | 状态 | “已过期”被定义为已发布后过期；自动任务却只写扫描待审核并转过期 | 两种迁移可并存但规则不完整 | 扫描范围、迁移优先级、可否恢复 |
| `ISSUE-CARRIER-001` | 业务规则 | 文档直接写“复核指什么？”和有效期过后如何显示 | 尚不能写死枚举或状态迁移 | 复核触发、宽限期、自动失效、通知 |
| `ISSUE-CARRIER-002` | 字典 | 创新企业/平台已有级别字段，类型字典又可能自带级别 | 会产生不合法组合 | “基础类型+级别”还是完整资质字典；合法组合 |
| `CONFLICT-OA-001` | 权威源 | 身份证、电话等字段写“OA同步，可更改” | 可能造成主数据冲突及敏感信息风险 | 覆盖权限、回写、留痕、脱敏、加密 |
| `ISSUE-IAM-001` | 权限 | 只提出按个人/单位/部门/角色/岗位等多维控制 | 尚无可开发权限矩阵 | 角色×动作×资源×数据范围×状态×字段 |
| `ISSUE-DATA-001` | 快照 | 自查、重大事项、终止、验收大量字段写“项目中获取” | 动态引用会改写历史语义，全部复制又会冗余 | 每字段实时引用或提交快照策略 |
| `ISSUE-PROJ-002` | 编号 | 项目号为年份-公司简称-递增号且系统唯一 | 未覆盖简称变更、并发、迁移冲突、作废重用 | 原子生成、不可变、保留号、迁移映射 |
| `ISSUE-MIG-001` | 迁移 | 不完整历史记录可按“最小必要集”导入 | 未定义则不可实施或验收 | 各对象最小集、去重、失败隔离、对账阈值 |
| `CONFLICT-PERF-001` | NFR | 同时出现1000在线/并发操作/并发用户；简单事务≤3秒和录入修改≤2秒 | 在线会话不等于并发请求，无法直接压测 | 峰值模型、比例、数据量、P95/P99、环境 |
| `ISSUE-MOBILE-001` | 异常 | M3要求实时双向同步 | 外勤存在断网、重复提交、附件失败 | 离线草稿、幂等、重试、冲突与失败提示 |
| `CONFLICT-DOC-001` | 文档污染 | 运维段落出现“应收账款逾期数据归集系统” | 模板复制残留，不是本项目范围 | 正式修订并全文校验 |

此外，正文业务多处依赖AI规划/匹配，但AI被列为后期功能；若AI后置，必须定义本期人工模板或规则降级路径。

## 8. 项目验收场景的提炼示例

### 来源事实

- **[事实]** 项目负责人发起验收，提交结题报告、成果清单和经费决算。
- **[事实]** 管理部门组织专家评审，系统记录意见与结论，通过后更新项目状态并归档。
- **[事实]** 未完成成果登记不得关闭项目。
- **[事实]** 要素表有申请日期、项目信息、验收形式/时间/地点、资料目录、最终验收时间。

### 候选设计

```yaml
id: KCMS-SCN-PROJ-008
name: 科研项目验收闭环
actor: 项目负责人
trigger: 项目达到验收条件
main_result: 验收结论、项目状态、成果关联和归档一致
facts:
  - 提交验收材料与成果清单
  - 管理部门组织评审并登记结论
  - 通过后进入已验收并归档
inferred_alternatives:
  - 材料不完整退回补正
  - 验收不通过后整改并重提
  - 受理前撤回
open_issues:
  - 验收条件、专家选择/回避、意见汇总
  - 不通过后的业务状态与重提次数
  - 经费决算来自财务同步还是文件
```

退回、整改、重提和撤回是**[分析推断]**的必要异常候选，不是文档事实。

候选验收标准：Given项目进入验收且要求成果未登记完整，When有权限用户尝试关闭项目，Then系统拒绝关闭、保持原状态并提示缺失项。是否记录失败操作审计仍需确认。

## 10. 结论

1. **[事实]** 两份材料足以启动需求精炼并形成较完整的候选能力、场景和字段目录。
2. **[分析推断]** 当前最大缺口是范围冲突、状态机、异常流程、字段权威源、权限矩阵、接口失败策略和可测试NFR，尚不宜直接做物理表和代码设计。
3. **[分析推断]** 需求阶段的核心产物应是带稳定编号、证据标签、双向追踪和质量门的结构化需求包。
4. **[待确认]** 应优先解决AI范围、实时/日更、直立/自立、项目/资讯状态、复核/有效期、OA覆盖和性能负载模型七组问题。

来源：`SRC-001` 与 `SRC-002` 均为用户提供的一手材料；本文件未把外部网络资料作为项目事实来源。
