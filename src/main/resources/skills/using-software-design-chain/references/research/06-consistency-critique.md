## 1. 证据边界

- **[事实]** 用户指定八段链：需求精炼 → 场景/规则/状态/权限 → 领域边界与聚合 → 数据模型与表设计 → 后端契约与代码架构 → 前端任务与页面设计 → 测试与验收 → 跨产物一致性审查。
- **[事实]** 用户允许使用 DDD 做边界设计，但不要求实现采用 DDD 四层；现有三层实现可把相应职责映射到 Service。
- **[事实]** `01-superpowers.md` 归纳了 Superpowers 的薄入口、组合技能、产物交接、执行前复核、任务级与全局评审、新鲜验证证据及结构化阻塞状态。
- **[事实]** `02-requirements.md` 已为需求、场景、规则、状态、权限、字段、接口和验收建议稳定类型 ID，并记录本项目 AI 范围、财务时效、术语、状态、权限等未决问题。
- **[事实]** `03-domain-boundaries.md` 区分语义边界、一致性边界、代码边界和部署边界；聚合来自不变式，不来自表、菜单或对象数量。
- **[事实]** `04-data-backend.md` 区分概念、逻辑、物理模型，并要求后端先定义用例/API/事务契约，再映射三层、四层、模块化单体或微服务。
- **[事实]** 女娲材料要求多维研究结果持久化、区分一手/二手/推断、保留冲突、设置研究与提炼检查点，并拒绝以编造换取表面完整。
- **[推断]** 女娲是本技能链的“构建期研究方法”，不应成为技能链运行时的必需依赖；否则每次设计项目都会重复造技能。

## 2. 对八段顺序的总体判断

- **[推断]** 顺序方向基本正确，但若解释成严格瀑布，会造成返工和假冻结。
- **[推断]** 第一段和第二段存在天然重叠，必须划清所有权，否则同一状态、规则和权限会被两次定义。
- **[建议]** “需求精炼”只负责范围、目标、角色、能力、来源、NFR、术语、冲突、优先级和验收意图。
- **[建议]** “场景建模”独占可执行行为：触发、前置、主/异常路径、业务规则、状态转换、权限决策、审计与业务结果。
- **[推断]** 领域阶段应始终识别能力、语义与所有权边界，但不应强迫每个 CRUD 模块都有聚合根。
- **[建议]** 若没有跨对象不变式，只输出一致性单元或简单服务候选，并说明“无需战术聚合”，不得造一个形式聚合。
- **[推断]** 数据阶段要消费领域所有权和不变式；先画完整物理表再找领域边界会固化错误职责。
- **[推断]** 后端阶段必须消费场景、权限、领域、数据模型；但 API 草案可在逻辑模型稳定后与物理 DDL 协同演进。
- **[推断]** 前端不应等后端全部完成才启动：信息架构、任务流和低保真页面可在场景稳定后开始；字段/API 绑定必须等契约稳定。
- **[推断]** 测试不是只在第七段出现：验收意图始于需求，Given/When/Then 始于场景，架构与契约测试在后续补齐；第七段负责汇总成可执行测试体系。
- **[推断]** 一致性审查也不是一次性末段；应“每段局部审查 + 末段全链审查”。

## 3. 建议的真实依赖图

| 阶段 | 硬输入 | 可提前进行 | 必须等待 |
|---|---|---|---|
| 需求精炼 | 建设方案、要素资料、现状约束 | 来源盘点、冲突扫描、术语提取 | 范围性重大冲突需责任人决定 |
| 场景建模 | 需求能力、角色、范围基线 | 独立模块的主/异常流程研究 | 核心角色、目标和范围可判定 |
| 领域边界 | 已确认核心场景、规则、状态、权限 | 通用语言、能力聚类候选 | 关键不变式和权威数据归属 |
| 数据设计 | 领域所有权、不变式、状态与查询需要 | 概念模型可随领域候选迭代 | 逻辑模型基线后才能冻结物理表 |
| 后端设计 | 用例、权限、边界、逻辑数据模型 | API/错误草案、项目现状探查 | 事务、字段和集成权威源须明确 |
| 前端设计 | 角色任务、场景、状态、权限 | IA、导航、任务流、低保真框架 | 详细字段/操作需 API 与错误契约 |
| 测试验收 | 全部可验证设计产物 | 需求/场景验收样例可提前写 | E2E、契约、性能计划需最终设计 |
| 一致性审查 | 版本化产物与追踪台账 | 每阶段增量审查 | 全链通过需所有阻塞项闭环 |

## 4. 哪些可以并行，哪些不能

- **[事实]** Superpowers 研究要求仅对相对独立任务采用隔离/并行，并在执行前检查任务冲突。
- **[建议]** 同一阶段的来源阅读、现状代码探查、术语提取、NFR提取可并行，汇总时由一个所有者合并。
- **[建议]** 已划分且共享术语很少的业务域可分别建模；共享组织、人员、流程、附件、字典等平台能力必须先统一契约。
- **[建议]** 领域基线通过后，数据逻辑模型、后端用例契约和前端 IA 可有限并行。
- **[建议]** 并行的前提是三方消费同一个基线版本，并把新增问题写回同一问题台账，而非各自修订上游事实。
- **[建议]** 物理 DDL 与持久化实现映射不宜完全并行；列、约束、事务与查询模型需要短周期收敛。
- **[建议]** API 详细契约与页面字段/操作矩阵可以按纵向切片并行，但每个切片只能有一个契约所有者。
- **[建议]** 功能测试、权限测试、契约测试、性能/安全计划可在设计稳定后并行，最终覆盖矩阵由测试阶段统一合并。
- **[禁止]** 不得同时让多个代理修改同一个基线文件或同一 ID 的语义。
- **[禁止]** 不得让数据、后端、前端代理各自补造缺失业务规则后再在末尾“求交集”。
- **[禁止]** 不得因为有代理槽位就把八段全部并发启动。

## 5. 必须阻塞的质量门

### Gate G0：来源与运行上下文

- 来源已登记版本、权威级别和适用范围；现有系统事实与建议分开。
- 项目标识、当前纵向切片、基线版本、用户目标和排除范围已知。
- 缺文件可输出缺口报告，但不得宣称需求基线完成。

### Gate G1：需求基线

- 核心范围、角色、业务目标、能力目录和术语可判定。
- 重大范围矛盾已有 `DEC-*`，例如 AI 是否本期、财务是实时还是日更。
- Must 需求和关键 NFR 有验收意图；未知项有责任人和影响。

### Gate G2：行为闭环

- 每项核心能力至少有主流程、适用异常、状态迁移和业务结果。
- 规则含条件、结果、例外和来源；权限含动作、资源、数据范围、状态和字段维度。
- 审批状态与业务状态不混用；无来源推断保持候选状态。

### Gate G3：边界与一致性

- 术语、能力、规则和数据各有权威归属；上下游契约可说明。
- 每个聚合候选列出具体不变式、事务与失败恢复；没有不变式时不造聚合。
- 设计边界与代码/部署选择分离，重大架构路线有 `ADR/DEC-*`。

### Gate G4：数据与后端可实现

- 概念、逻辑、物理模型不混为一份表格；关键规则映射到约束或应用校验。
- 每个写用例有权限、事务、并发、幂等、错误、审计和集成副作用。
- API、Service、表/事件、错误和审计之间有可验证映射。

### Gate G5：前后端收敛

- 每个页面动作绑定用例/API，状态与权限决定可见、可用和失败表现。
- 表单字段在 API 和数据字典中有来源；前端不得私自增加业务状态或枚举。
- 加载、空、错误、冲突、超时、重复提交和数据时间戳均有设计。

### Gate G6：测试与验收就绪

- 每项 Must/NFR、规则、状态、权限和契约至少有测试或明确验证方法。
- 测试数据、环境、外部依赖替身、性能负载和验收责任人可执行。
- 只有文档存在、示例成功或单元测试通过，均不足以宣称系统设计完成。

### Gate G7：全链一致性

- 阻塞/严重问题为零；所有豁免都有责任人、理由、到期日和决策 ID。
- 无孤儿需求、孤儿页面、孤儿 API、孤儿表/字段、孤儿测试或无消费者事件。
- 完成声明绑定刚产生的验证报告、产物版本和批准记录。

## 6. 稳定 ID 与追踪协议

- **[事实]** `02-requirements.md` 已建议 `KCMS-SCN-*`、`KCMS-BR-*`、`KCMS-STM-*`、`KCMS-PERM-*`、`KCMS-FLD-*`、`KCMS-INT-*`、`KCMS-AC-*` 等类型化编号。
- **[建议]** 使用 `{PROJECT}-{TYPE}-{DOMAIN}-{SEQUENCE}`，例如 `KCMS-SCN-PROJ-008`；序号无业务含义且永不复用。
- **[建议]** 稳定 ID 不含文档章节号、阶段号、状态、年份版本或文件路径，避免重排章节后全部失效。
- **[建议]** 每个对象至少记录：`id`、`type`、`title`、`status`、`version`、`owner`、`source_refs`、`confidence`、`upstream_refs`、`decision_refs`、`verification_refs`。
- **[建议]** ID 标识语义对象，版本标识某次内容；修改内容不换 ID，语义拆分/合并则新建 ID 并记录 `supersedes/replaced_by`。
- **[建议]** 被撤销对象保留 `retired` 状态和替代关系，不物理删除，不把原编号分配给新含义。
- **[建议]** 关系必须有类型，至少包含 `derives_from`、`realizes`、`persists_as`、`exposes`、`renders`、`verifies`、`conflicts_with`、`supersedes`。
- **[建议]** 建立唯一权威 `artifact-registry` 和 `traceability-ledger`；各 Markdown 表只是投影，不能各自维护一套真相。
- **[建议]** 典型链路为 `SRC/CAP/REQ -> SCN -> BR/STM/PERM -> CTX/AGG/CMD -> ENT/TBL -> UC/API/SVC/EVT -> PAGE/ACTION -> TC/AC`。
- **[建议]** 允许一对多、多对一，但任何跳跃都要解释；例如页面可聚合多个查询 API，聚合可映射多张表。
- **[建议]** 每次阶段输出生成“新增、修改、废弃、断链、冲突”差异，而不是重写一份无法比较的全量文档。

## 7. 总入口如何避免无限循环

- **[推断]** 总入口必须是有限状态编排器，而不是“调用所有技能直到看起来完成”的自由代理。
- **[建议]** 维护 `design-chain-manifest`：`run_id`、`slice_id`、当前阶段、阶段版本、Gate 状态、阻塞问题、批准、路由历史和下一允许动作。
- **[建议]** 一次路由只选择一个阶段或一个明确并行组；阶段技能完成后把结构化状态返回入口。
- **[建议]** 阶段状态固定为 `READY`、`READY_WITH_ASSUMPTIONS`、`NEEDS_CONTEXT`、`BLOCKED`、`REVISE_UPSTREAM`、`FAILED_VALIDATION`。
- **[建议]** 被入口调用的阶段收到 `invoked_by=using-software-design-chain`，禁止再次调用总入口；这对应 Superpowers 对被派发代理避免递归路由的做法。
- **[建议]** `REVISE_UPSTREAM` 必须携带具体问题 ID、受影响 ID、目标阶段、修复条件和影响范围，不能只说“需求不清”。
- **[建议]** 同一问题自动回退最多一次；第二次仍无新证据或决策时必须转 `NEEDS_CONTEXT/BLOCKED`。
- **[建议]** 比较本轮输入/输出摘要；若连续两次产物哈希、开放问题和 Gate 结果无实质变化，判定无进展并停止。
- **[建议]** 对每个运行设置阶段访问上限和总回退预算；预算是故障保护，不是绕过 Gate 的许可证。
- **[建议]** 用户追加资料后创建新运行或恢复点，不从头重做已通过且未受影响的阶段。
- **[建议]** 影响分析只重新打开被变更 ID 可达的下游产物，避免一处文案变更触发整链重跑。

## 8. 如何避免假完成和凭空补全

- **[事实]** Superpowers 研究明确区分“文件存在/测试通过”与“声明范围被证据覆盖”；女娲材料也要求宁可承认不足，不以编造换完整。
- **[建议]** `READY` 只能由 Gate 检查器产生，不能由阶段作者自行口头宣称。
- **[建议]** `READY_WITH_ASSUMPTIONS` 只允许进入不依赖该假设的探索性工作，不能形成正式基线或最终完成。
- **[建议]** 每条内容标记 `CONFIRMED`、`SOURCE_FACT`、`INFERRED`、`PROPOSED`、`OPEN`、`REJECTED`；下游不得自动提升证据等级。
- **[建议]** 缺少业务规则时输出 `OPEN/DECISION_REQUIRED`，不得用“通常系统会……”填成既定要求。
- **[建议]** `N/A` 必须附决策 ID 和理由，防止通过大量“不适用”清空检查项。
- **[建议]** 禁止 `TBD/TODO/后续完善/按实际情况` 等伪交付；确实未知时进入问题台账并说明阻塞范围。
- **[建议]** 自动修复仅限 ID 引用、格式、重复项和已确认术语替换；业务语义、权限、状态、数据删除和架构取舍不得自动修复。
- **[建议]** 主观决策设置人工检查点：范围基线、核心状态/权限、领域边界、数据隔离、架构路线、最终验收。
- **[建议]** 验证报告必须列出运行时间、输入产物版本、检查器版本、通过/失败明细，旧报告不能证明新版本。

## 9. 跨产物一致性应检查什么

| 规则族 | 必查断链/冲突 |
|---|---|
| 术语 | 同名异义、异名同义、上下文未限定、前端文案改变业务含义 |
| 范围 | 范围外能力进入表/API/页面/测试；Must 需求无实现设计 |
| 状态 | 状态值、允许转换、审批态、API 命令、页面动作和测试不一致 |
| 权限 | 角色、数据范围、字段权限、后端鉴权、前端可见性和越权测试不一致 |
| 数据 | 权威源、快照、历史、可空性、枚举、精度、时区、删除/保留不一致 |
| 边界 | 一个对象多写入者、跨边界写表、循环依赖、契约绕过 |
| API | 用例缺端点、端点无用例、字段漂移、错误无 UI 行为、幂等缺测试 |
| 前端 | 页面动作无业务结果、直接修改状态、孤儿字段、异常/冲突状态缺失 |
| 集成 | 同步频率与“实时”文案冲突、失败/重试/对账无页面和运维责任 |
| NFR | 性能、安全、审计、国产化、备份等承诺无架构措施或验收方法 |
| 测试 | 只测主流程、规则/权限/状态/契约/NFR 无覆盖，验收主体不明 |

- **[建议]** 严重度至少分 `BLOCKER`（需业务/架构决策）、`CRITICAL`（语义或实现矛盾）、`MAJOR`（断链/覆盖缺口）、`MINOR`（表达/格式）。
- **[建议]** `BLOCKER/CRITICAL` 未闭环不得过 Gate；`MAJOR` 只能凭明确豁免继续；`MINOR` 可进入修订队列。
- **[建议]** 一致性审查保持只读，只提交问题与补丁建议；原产物所有者负责修改，审查者再验证。

## 10. 与 Superpowers、女娲及现有技能的复用边界

- **[事实]** Superpowers 的核心模式是可组合技能和薄入口，不是一个巨型万能技能。
- **[建议]** `using-software-design-chain` 只在用户要求“从方案到完整设计”、继续整条设计链或检查链路状态时触发。
- **[建议]** 用户只要求表设计、前端页面或测试方案时，直接触发对应阶段技能；它先验证上游，不强制启动整链。
- **[建议]** 阶段技能 description 使用窄触发词和明确产物，避免九个技能都被“软件设计/架构”同时命中。
- **[建议]** 优先级：显式点名阶段技能 > 显式整链 > 单一产物任务 > 实现/修复任务。
- **[建议]** 若请求同时含设计与实现，先完成并批准设计链相关切片，再交给 Superpowers 的计划/实现/评审流程。
- **[建议]** 可复用 Superpowers 的 brainstorming、计划、评审、验证方法，但不要在运行时硬依赖未安装的技能名；能力不可用时执行本链内置最小流程。
- **[建议]** 女娲仅用于创建/更新这组技能时的研究、提炼和质量检查；生成后的技能必须自包含。
- **[建议]** `documents` 负责读取/生成/渲染文档，不拥有业务需求决策；`skill-creator` 负责技能结构与验证，不拥有软件设计方法。
- **[建议]** 旧 DDD/自适应架构技能应标为迁移来源、兼容别名或弃用，不与新阶段技能共享宽泛触发描述。
- **[建议]** `design-domain-boundaries` 负责设计语义，`design-backend-architecture` 负责实现映射；两者不得都宣称拥有最终聚合/代码目录决定。
- **[建议]** `design-data-model` 负责数据语义与物理模型，`design-backend-architecture` 只能消费或提出变更，不能静默重写表设计。
- **[建议]** `review-design-consistency` 为只读审查技能，不应自动调用自身，也不直接修复所有产物。

## 11. 主要风险与缓解

| 风险 | 结果 | 缓解 |
|---|---|---|
| 九技能描述过宽 | 同时触发、重复工作、不同结论 | 窄 description、显式优先级、`invoked_by` |
| 第一/二段职责重复 | 状态和规则两套真相 | 需求管意图，场景管可执行行为 |
| 过早物理表设计 | 页面字段绑死存储与边界 | 概念→逻辑→物理三段门 |
| DDD 被实现化 | 被迫四层/微服务/形式聚合 | 战略设计稳定，战术实现可替换 |
| 并行代理补造事实 | 合并时出现隐性冲突 | 单一台账、证据等级、单作者原则 |
| 回退无停止条件 | 无限循环、成本失控 | 问题 ID、回退预算、无进展检测 |
| 检查清单驱动假完成 | 形式齐全但不可实施 | 新鲜证据、语义抽查、人工 Gate |
| 追踪只靠文档链接 | 文件重命名后断链 | 稳定 ID、权威注册表、关系类型 |
| 最终才做审查 | 错误级联到所有产物 | 每阶段增量审查 + 全链审查 |
| 直接复用外部技能名 | 未安装即失败、行为漂移 | 能力检测、内置最小流程、版本记录 |

## 12. 最终研究结论

1. **[推断]** 八段技能链可成立，但应解释为“有 Gate 的增量图”，不是不可回退的线性瀑布。
2. **[推断]** 领域边界阶段应强制，战术聚合和 DDD 代码结构不应强制；这最符合用户“设计用 DDD、实现适配现状”的要求。
3. **[推断]** 数据、后端和前端可以部分并行，但只能在稳定场景/边界基线与单一追踪台账之上进行。
4. **[推断]** 测试与一致性是贯穿活动，第七、八段是体系化收敛与最终 Gate，不是首次考虑。
5. **[推断]** 总入口的核心资产应是状态机、产物注册表、追踪台账、决策/问题台账和停止条件，而不是更长的提示词。
6. **[推断]** 最可靠的完成定义是：阻塞归零、稳定 ID 无断链、每项声明有新鲜证据、主观决策已批准、下游没有把推断升级成事实。
7. **[待确认]** 最终技能应决定正式基线由谁批准、允许多少非阻塞假设、跨模块共享能力由谁拥有，以及旧两个架构技能采用兼容别名还是直接弃用。
