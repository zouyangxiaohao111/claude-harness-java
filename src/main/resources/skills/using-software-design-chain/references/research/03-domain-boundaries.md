## 研究目的

为软件设计技能链提供与实现架构中立的领域建模规则：使用 DDD 战略设计识别语义边界、职责边界、一致性边界和演进单元，但不强制采用 DDD 四层代码结构、富领域模型或微服务。

重点回答：

1. 如何从建设方案和业务场景得到领域、限界上下文与聚合候选；
2. 如何把同一领域设计映射到三层、四层、模块化单体或微服务；
3. 哪些 DDD 原则只能作为启发式规则；
4. 如何保持需求、领域模型、代码与测试可追踪。

## 章节来源

来源为用户提供的《中台架构与实现：基于DDD和微服务》（欧创新、邓頔）：

- 第3章：DDD 是设计方法，微服务是架构风格；DDD 也可用于单体。
- 第5章：领域和子域用于逐级分解问题域；子域分类用于资源投入策略。
- 第6章：通用语言与限界上下文限定语义和模型适用范围；限界上下文不是微服务拆分的唯一标准。
- 第8章：聚合封装业务不变条件和一致性边界；书中也要求结合项目实际使用聚合原则。
- 第9章：领域事件可用于解耦，但同一服务内的多聚合更新也可按一致性要求选择本地事务。
- 第10—11章：四层、洋葱、六边形形式不同，共性是业务逻辑与技术细节分离；三层可演进为更清晰的职责划分。
- 第12章：事件风暴从愿景、场景、命令、事件、实体形成聚合和上下文；事件风暴不是唯一建模手段。
- 第14—15章：领域对象与代码对象应显式映射；DDD 本身没有规定唯一代码模型。
- 第16章：逻辑边界、物理边界和代码边界不要求一一重合，边界应支持低成本演进。
- 第23章：反对所有领域套完整 DDD、只重战术模式、所有系统都做微服务；允许传统查询方法、贫领域模型和单体实现。

下文的中立规则、实现映射和技能输出契约是基于这些章节的综合设计，不是书中原文。

## 核心结论

### 1. DDD 是设计语言，不是实施命令

- **战略设计**：通用语言、子域、限界上下文、上下文关系、业务能力、聚合候选。适用于单体和分布式系统。
- **战术实现**：聚合根类、实体方法、值对象、领域服务、仓储、领域事件、四层目录。应按业务复杂度和现有架构选择采用。

不得从“用 DDD 划分边界”推导出“必须采用四层架构”或“必须使用微服务”。

### 2. 设计边界与部署边界是两个决策轴

| 边界 | 回答的问题 | 主要证据 | 可能实现 |
|---|---|---|---|
| 语义/职责边界 | 术语在哪个范围含义一致，哪些职责共同演进 | 术语、规则归属、数据权威、上下游 | 模块、包、组件、服务 |
| 一致性边界 | 哪些状态在一次操作结束时必须共同满足不变式 | 不变式、并发、生命周期、事务 | 对象组、Service 内部模型、Repository 单元 |
| 物理边界 | 哪些能力需要独立部署、扩缩容或隔离 | 性能、安全、技术、发布、团队、运维 | 单体模块、服务、微服务 |

允许：

- 一个限界上下文先落在模块化单体的一个模块；
- 多个上下文在同一部署单元内保持代码隔离；
- 一个上下文因性能、安全或技术异构拆成多个部署单元；
- 聚合作为一致性和演进单元，而不独立部署。

### 3. 子域与限界上下文不能从菜单、表或包名直接推导

子域候选需结合业务目标、价值、流程阶段、规则集合、数据权威、变化原因和投入策略。核心/通用/支撑分类只决定关注度，不决定部署方式。

限界上下文候选需验证：

- 关键术语在边界内含义是否唯一；
- 模型、规则和状态是否围绕主要职责；
- 数据权威和进入/离开边界的契约是否清晰；
- 是否需要共享模型、翻译或防腐层；
- 能否相对独立演进。

子域与上下文不要求一对一。复杂子域可有多个上下文；小问题域可直接建模。

### 4. 聚合从不变式和事务需求识别

核心问题是：**一次业务命令结束时，哪些对象的哪些条件必须同时成立？**

证据包括：

- 明确的不变式；
- 共同生命周期；
- 受控修改入口；
- 并发冲突概率；
- 强一致、延迟、补偿和人工恢复要求；
- 是否需要保存当时事实的不可变快照。

不得用“主从表”“外键”“同一页面”“固定对象数量或代码行数”直接判定聚合。找不到聚合根也不等于失败；统计、批处理和复杂查询可以用过程式 Service、SQL 或 CQRS 读模型。

### 5. 领域事件是业务事实，异步消息只是实现选择

| 情形 | 优先候选 | 检查点 |
|---|---|---|
| 同进程且必须立即强一致 | 本地事务或同步调用 | 原子性、锁、事务范围 |
| 同进程且后续动作可延迟 | 进程内事件或任务 | 重试、顺序、幂等 |
| 跨部署且允许最终一致 | Outbox/可靠事件与消息 | 投递、重复、对账、补偿、观测 |
| 跨部署且必须同步获知结果 | 同步契约，必要时 Saga/补偿 | 超时、级联故障、部分失败 |

不得因为跨聚合就自动引入消息中间件，也不得只画事件箭头而遗漏幂等、重试、顺序、补偿、对账和失败责任。

### 6. 代码映射必须可追踪，不必一一对应

| 设计项 | 最小代码映射 |
|---|---|
| 限界上下文 | 模块/包/服务位置、公开契约、数据所有者 |
| 聚合/一致性单元 | 修改入口、事务边界、持久化入口、不变式位置 |
| 命令/用例 | Controller/Handler、编排位置、授权点 |
| 业务规则 | 类/函数/规则引擎位置、需求和测试编号 |
| 领域事件 | 产生、发布、订阅、幂等和补偿位置 |
| 查询模型 | 查询服务/DAO/视图/索引、数据新鲜度 |

允许多对一或一对多映射，但必须说明原因，并能从需求追踪到代码和测试。

## 实现架构中立映射

### 三层架构

三层可以承载领域设计。即使领域职责物理上都落在 Service 层，也要保持内部角色可定位：

| 设计职责 | 三层实现 |
|---|---|
| 接口与 DTO 适配 | Controller、DTO、Mapper |
| 用例编排、事务、权限 | `*Service` 公开方法或 `*UseCase` |
| 规则、不变式、状态转换 | Service 内部规则类、策略类、实体方法或明确函数 |
| 数据访问 | DAO/Mapper/Repository |
| 外部系统 | Client/Gateway/Adapter |

验收重点不是有无 `domain/` 目录，而是规则有唯一且可测试的位置、Controller 不承载核心规则、SQL/ORM 对象不成为跨模块共享模型、跨模块调用走明确契约。

### 四层、Clean、Hexagonal

- Port 是应用提供或依赖的契约，不等于聚合根接口；
- Clean Architecture 的 Entity 不必然等同 DDD 聚合根；
- Repository 接口目录是团队约定，关键是依赖方向与职责隔离；
- 严格逐层调用可作为项目规范，但不是无条件领域规则。

### 模块化单体

- 以限界上下文或稳定业务能力建立模块；
- 每个模块声明公开 API，隐藏内部表、类和实现；
- 模块间不得绕过契约直接修改对方数据；
- 先保持代码边界，再按性能、安全、团队或发布要求演进部署边界。

### 微服务

只在独立部署确有收益且团队具备运行能力时选择。决策需记录业务依据、部署收益、数据所有权、同步/异步契约、一致性和补偿、发布监控能力及团队所有权。“一个上下文一个微服务”只能作为候选起点。

## 建议流程

1. **检查输入**：范围、目标、角色、术语、主/异常场景、命令、事件、状态、规则、权限、外部依赖及未知项。
2. **建立通用语言**：记录术语、定义、上下文、同义词、歧义和来源需求。
3. **形成子域候选**：按业务能力、价值、流程和规则所有者聚类。
4. **串联场景**：`角色/触发器 -> 命令 -> 前置条件 -> 规则 -> 状态变化/事件 -> 后续动作 -> 异常/补偿`。
5. **识别上下文**：填写使命、包含/排除范围、术语、数据权威、公开能力、上下游和变化原因。
6. **识别一致性单元**：逐条命令检查不变式、事务、并发、生命周期和失败恢复，再决定是否使用聚合根等战术模式。
7. **建立关系图**：记录上下游、数据权威、契约、翻译、时延和失败责任；循环依赖是审查信号，不能为图形无环而隐藏事实。
8. **选择实现形态**：根据现有架构、团队、性能、安全、发布频率和运维成本映射到三层、四层、模块化单体或微服务。
9. **验证边界**：用主流程、异常、并发、失败恢复、查询和未来重组场景检验。

输入不完整时可输出候选模型，但必须标置信度、假设和待确认项，不能把推断写成业务事实。

## 输出契约

领域边界技能至少输出：

1. `UBI-*` 通用语言；
2. `SUB-*` 子域与投入策略；
3. `CTX-*` 限界上下文目录；
4. `CTX-REL-*` 上下文关系；
5. `CAP-*` 业务能力；
6. `AGG-*` 聚合/一致性候选及不变式；
7. `CMD-*` 命令与用例归属；
8. `EVT-*` 领域事件及异步决策；
9. `MAP-*` 设计到代码架构映射；
10. `DEC-*` 架构决策；
11. `OPEN-*` 未决项、假设、风险和置信度。

每项必须引用上游需求/场景/规则编号。下游发现冲突时应提出变更并回写决策，不得静默漂移。

## 不可机械照搬的规则

| 机械规则 | 中立替代规则 |
|---|---|
| 一个上下文就是一个微服务 | 先作部署候选，再结合非功能需求和运维能力决策 |
| 一个聚合就是一个微服务 | 聚合是最小一致性/演进候选，不代表独立部署 |
| 一次事务最多修改一个聚合 | 默认缩小事务；业务原子性更强时可协调多个单元并记录权衡 |
| 跨聚合一律使用事件 | 按一致性、时延、失败和复杂度选择事务、同步或可靠异步 |
| 聚合只能通过根 ID 关联 | 禁止越界修改内部对象；查询、快照和同进程只读引用按场景评估 |
| 一个聚合只能有一个仓储 | 默认统一修改语义；多数据源可有多个适配器 |
| 所有实体都必须充血 | 核心复杂规则用行为模型，CRUD/查询/统计可用简单对象与过程式服务 |
| 所有服务必须严格逐层 | 依赖方向和职责清晰是目标，是否禁止跨层由项目决策 |
| 领域对象与代码类一一对应 | 必须可追踪，但允许多对一/一对多并说明原因 |
| 上下文依赖绝对无环 | 循环是风险信号，应拆责或引入契约，不能伪造模型 |
| 先设计全套表再找聚合 | 先识别规则和一致性，再设计数据模型；旧表仅作约束和证据 |

## 质量检查与技能链约束

- 核心术语、规则、状态和数据是否各有唯一权威归属？
- 聚合候选是否列出具体不变式，而非对象清单？
- 一致性选择是否由业务驱动，并定义失败恢复？
- 设计边界与物理部署是否分开决策？
- 三层实现中能否定位编排、规则和数据访问？
- 查询是否穿透其他上下文私有表；是否需要读模型或数据产品？
- 结论是否可追踪到需求、场景、代码和测试？

`design-domain-boundaries` 必须消费已经确认的场景、规则、状态和权限，不能从字段表直接生成聚合；数据技能可采用不同物理表映射，但须保持数据权威和不变式；后端技能先选实现形态再映射同一领域设计；前端按用例、状态与权限设计页面；测试覆盖不变式、状态转换、契约和失败路径；一致性审查检查术语、规则、数据、API、代码和测试映射。

## 最终原则

稳定资产是通用语言、业务能力、语义边界、规则归属、一致性要求和上下文契约。四层目录、聚合根类、仓储接口、消息中间件和微服务只是可替换的实现选择。

完整技能链应坚持：**设计上边界明确，实施上架构适配，映射上全程可追踪，演进时允许重新决策。**
